# Miden data model for an external block explorer indexer

Scope: Polygon Miden node **v0.13.4** public RPC, as exposed by this repo's copied protos under `proto/proto/`. This document is written for an external block explorer indexer that is **not** a transaction participant and has no off-chain note/account data unless a user submits it. Official protocol references are inline; local proto references are treated as v0.13.4 API observations.

## 1. Primitives

### Block

**Definition.** A block is the node's sequenced state transition unit. The public RPC can return either a structured `BlockHeader` or raw serialized `Block` bytes (`MaybeBlock.block`) encoded with the Rust `winter_utils::Serializable` implementation for `miden_protocol::block::Block` (`proto/proto/types/blockchain.proto`; upstream: <https://raw.githubusercontent.com/0xMiden/node/v0.13.4/proto/proto/types/blockchain.proto>). The node README states that Miden node receives transactions and sequences them into blocks, and that v0.13.4 is still alpha and centralized-operator oriented, with P2P networking and consensus not yet included (<https://raw.githubusercontent.com/0xMiden/node/v0.13.4/README.md>).

**Header fields.** `BlockHeader` contains: `version`, `prev_block_commitment`, `block_num`, `chain_commitment`, `account_root`, `nullifier_root`, `note_root`, `tx_commitment`, `validator_key`, `tx_kernel_commitment`, `fee_parameters`, and `timestamp` (`proto/proto/types/blockchain.proto`; upstream link above). `GetBlockHeaderByNumber` may also return an MMR path and chain length proving block inclusion (`proto/proto/rpc.proto`; upstream: <https://raw.githubusercontent.com/0xMiden/node/v0.13.4/proto/proto/rpc.proto>).

**Identity.** The header commitment/hash is represented in the API as `primitives.Digest` where relevant; a digest is four `fixed64` lanes (`d0..d3`), i.e. 32 bytes of field data on the public protobuf API (`proto/proto/types/primitives.proto`; upstream: <https://raw.githubusercontent.com/0xMiden/node/v0.13.4/proto/proto/types/primitives.proto>). Blocks are also addressable by `block_num` (`fixed32`) in the public RPC (`proto/proto/types/blockchain.proto`).

**Lifecycle.** The block producer samples mempool transactions into batches, proves those batches, periodically aggregates batches into a block, proves the block, and commits it to the store (<https://docs.miden.xyz/core-concepts/node/operator/architecture/>). The store persists chain state and exposes it to the public RPC through the RPC component (<https://docs.miden.xyz/core-concepts/node/operator/architecture/>).

### Transaction

**Definition.** A Miden transaction is the state transition of a **single account**; it takes one account and zero or more notes as input and outputs the same account with updated state and zero or more notes (<https://docs.miden.xyz/core-concepts/protocol/transaction>). Transaction execution produces a zero-knowledge proof; local transactions enable privacy because neither account state nor account code are needed to verify the proof, and public inputs are commitments plus block information (<https://docs.miden.xyz/core-concepts/protocol/transaction#local-transaction>).

**Fields visible through public RPC.** `TransactionId` is a `Digest`; `TransactionSummary` contains `transaction_id`, `block_num`, and affected `account_id`; `TransactionHeader` contains `account_id`, `initial_state_commitment`, `final_state_commitment`, input-note `nullifiers`, and output `NoteSyncRecord`s (`proto/proto/types/transaction.proto`; upstream: <https://raw.githubusercontent.com/0xMiden/node/v0.13.4/proto/proto/types/transaction.proto>). `SyncTransactions` returns records only for requested account IDs over a block range (`proto/proto/rpc.proto`). There is no public RPC method in v0.13.4 protos named `GetTransactionById` or a global transaction stream (`proto/proto/rpc.proto`).

**Identity.** `TransactionId.id` is a 32-byte `primitives.Digest` (`proto/proto/types/transaction.proto`; `proto/proto/types/primitives.proto`).

**Lifecycle.** A proven transaction is submitted via `SubmitProvenTransaction`; the RPC validates/verifies and forwards accepted transactions to the block producer, which batches them for inclusion (<https://docs.miden.xyz/core-concepts/node/operator/architecture/>; `proto/proto/rpc.proto`). The operator checks nullifiers during verification; local transaction execution itself does not check nullifiers (<https://docs.miden.xyz/core-concepts/protocol/transaction>).

### Account

**Definition.** An account is Miden's primary entity: it can hold assets, store data, and execute custom code; each account is a smart contract with code, storage, vault, nonce, and ID (<https://docs.miden.xyz/core-concepts/protocol/account/>). Accounts are tracked in an authenticated sparse Merkle tree account database that tracks state commitments of all accounts and stores account data for public accounts (<https://docs.miden.xyz/core-concepts/protocol/state/#account-database>).

**Fields.** `AccountId` is a 120-bit value serialized as 15 bytes in the protobuf API (`proto/proto/types/account.proto`). `AccountHeader` contains `account_id`, `vault_root`, `storage_commitment`, `code_commitment`, and `nonce` (`proto/proto/types/account.proto`). `AccountSummary` contains `account_id`, current account commitment, and block number (`proto/proto/types/account.proto`). `AccountWitness` contains the requested account ID, witness ID, state commitment, and sparse Merkle path (`proto/proto/types/account.proto`).

**Identity.** Account IDs are immutable 120-bit numbers generated by hashing a seed with initial code/storage commitments until the desired type/storage-mode bits are obtained; the 256-bit hash is shortened to 120 bits (<https://docs.miden.xyz/core-concepts/protocol/account/id>). Bech32 is preferred for user-facing apps, and hex is used in CLIs/explorers (<https://docs.miden.xyz/core-concepts/protocol/account/id#encoding>).

**Lifecycle.** A locally generated ID is not network-recognized until it appears in the account database; the docs describe first registration when a user consumes a note in a transaction against the new account (<https://docs.miden.xyz/core-concepts/protocol/account/#account-creation>). Public/network accounts store state on-chain; private accounts store only a commitment/hash on-chain (<https://docs.miden.xyz/core-concepts/protocol/account/id#account-storage-mode>).

### Note

**Definition.** A note is the medium by which accounts communicate; it holds assets and defines how it can be consumed (<https://docs.miden.xyz/core-concepts/protocol/note>). Notes have assets, script, storage, serial number, and metadata (<https://docs.miden.xyz/core-concepts/protocol/note#note-core-components>). The note database records notes in an append-only Merkle Mountain Range (<https://docs.miden.xyz/core-concepts/protocol/state/#note-database>).

**Fields.** `NoteId` is a 32-byte commitment to the underlying note data (`proto/proto/types/note.proto`). `NoteMetadata` contains sender account ID, note type (`0b01 = public`, `0b10 = private`, `0b11 = encrypted`), 32-bit tag, and serialized attachment (`proto/proto/types/note.proto`). The docs say metadata fields are always public regardless of storage mode (<https://docs.miden.xyz/core-concepts/protocol/note#metadata>). `Note.details` is serialized note details and is empty for private notes; network notes are a subtype of public notes and their details are always publicly known (`proto/proto/types/note.proto`).

**Identity.** `NoteId.id` is a `Digest` commitment to the note data (`proto/proto/types/note.proto`). The note recipient is a 32-byte value computed as `hash(hash(hash(serial_num, [0; 4]), script_root), storage_commitment)` (<https://docs.miden.xyz/core-concepts/protocol/note#note-recipient-restricting-consumption>). The note nullifier is computed from `hash(serial_num, script_root, storage_commitment, vault_hash)` (<https://docs.miden.xyz/core-concepts/protocol/note#note-nullifier-ensuring-private-consumption>).

**Lifecycle.** The note lifecycle is creation, validation, discovery, and consumption (<https://docs.miden.xyz/core-concepts/protocol/note#note-lifecycle>). Public notes store full note data in the note database; private notes store only the note hash publicly and keep actual note data off-chain (<https://docs.miden.xyz/core-concepts/protocol/note#note-storage-mode>). A consumed note produces a nullifier that the operator records as consumed (<https://docs.miden.xyz/core-concepts/protocol/note#note-consumption>).

### Nullifier

**Definition.** Each note has an associated nullifier that tracks whether the note has been consumed and prevents double-spending (<https://docs.miden.xyz/core-concepts/protocol/state/#nullifier-database>). The nullifier database is a sparse Merkle tree; for each nullifier Miden records the block in which it was created/consumed, with block `0` representing unconsumed and non-zero blocks representing consumed nullifiers (<https://docs.miden.xyz/core-concepts/protocol/state/#nullifier-database>).

**Fields.** Public RPC nullifier APIs use `primitives.Digest` nullifier keys; `SyncNullifiersResponse.NullifierUpdate` returns `nullifier` plus `block_num` (`proto/proto/rpc.proto`). `CheckNullifiers` returns SMT openings proving inclusion or non-inclusion against the nullifier tree root (`proto/proto/rpc.proto`).

**Identity.** A nullifier is a 32-byte digest (`proto/proto/types/primitives.proto`) computed from note data as above; to compute it one must know the note's `serial_num`, `script_root`, `storage_commitment`, and `vault_hash` (<https://docs.miden.xyz/core-concepts/protocol/note#note-nullifier-ensuring-private-consumption>).

**Lifecycle.** When a note is successfully consumed, the operator records the note's nullifier as consumed in the nullifier database, extinguishing the one-time claim (<https://docs.miden.xyz/core-concepts/protocol/note#note-consumption>). Nullifiers break linkability for privately stored notes: to know a note's nullifier, one must know the note data (<https://docs.miden.xyz/core-concepts/protocol/state/#nullifier-database>).

## 3. Indexer scope matrix

Suggested tables are intentionally stable names for the schema agent: `miden_blocks`, `miden_transactions`, `miden_notes`, `miden_nullifiers`, `miden_accounts`, `miden_indexer_progress`.

| Primitive / table | MVP (v1) | Full public scope |
|---|---|---|
| Blocks — `miden_blocks` | Store one row per `block_num` from `GetBlockHeaderByNumber`: all structured header fields, canonical digest strings, timestamp, optional MMR proof if collected, ingestion time. | Also store raw `GetBlockByNumber` bytes and decoded body fields once a v0.13.4 block decoder is integrated; keep MMR chain length/proofs for audit views. |
| Transactions — `miden_transactions` | Store transaction summaries/headers only when obtained through `SyncState`/`SyncTransactions` for indexed accounts; include `tx_id`, `block_num`, `account_id`, initial/final commitments, nullifier list, output note IDs. Mark coverage as **account-scoped, not global**. | Decode raw block bodies or use any future global tx RPC to capture all transaction IDs and headers; add proof/status metadata if exposed. Deferred because v0.13.4 public proto has no global `GetTransactionById`/list-all-txs endpoint. |
| Accounts — `miden_accounts` | Store account ID, storage mode inferred from ID bits when SDK support is available, latest account commitment, block number, and public account header if `GetAccount(details=...)` returns it. | For public/network accounts, page and store code bytes, storage headers/map entries, vault assets and per-block updates from `SyncAccountVault` and `SyncAccountStorageMaps`. Defer exhaustive public storage/vault indexing because endpoints are account-specific and paginated/limited. |
| Notes — `miden_notes` | Store note sync records discovered by configured tags: `note_id`, block number, note index, metadata, inclusion path, note type, and whether details are present. Do not claim complete note coverage unless tags cover all desired public notes. | Store all publicly discoverable notes by broad tag strategy or raw block decode; decode public/network note details into assets, recipient, script/root/storage/serial fields. Defer because tag search is best-effort and details are serialized protocol bytes. |
| Nullifiers — `miden_nullifiers` | Store nullifier digest and consumed `block_num` from `SyncNullifiers` for configured 16-bit prefixes; for MVP, either index all 65,536 prefixes in chunks or record prefix coverage in progress. | Maintain complete nullifier set with inclusion/non-inclusion proof material if needed; support prefix scans and `/nullifier/:hex`. Nullifier set is public and required for double-spend checks, but scanning all prefixes can be operationally heavy. |
| Progress — `miden_indexer_progress` | Store last indexed block header, per-stream cursors (`headers`, `notes:<tag>`, `nullifiers:<prefix-range>`, `accounts`, `transactions`), chain tip observed, and node version/status. | Add revalidation checkpoints: header MMR proofs, root consistency checks, and coverage manifests for tags/prefixes/accounts. |

## 4. Identity and encoding

| Item | Wire/API representation | Size | Canonical explorer/DB string |
|---|---|---:|---|
| `BlockNumber` | `fixed32 block_num` | 4 bytes | Decimal integer without leading zeroes (`/block/123`). Source: `proto/proto/types/blockchain.proto`. |
| `Digest` / roots / commitments / tx IDs / note IDs / nullifiers | `primitives.Digest { fixed64 d0,d1,d2,d3 }` | 32 bytes | `0x` + 64 lowercase hex chars. | `AccountId` | `bytes id` encoded with `winter_utils::Serializable` for `AccountId`; docs define it as 120-bit | 15 bytes | Prefer Bech32 for user-facing URLs when network HRP is known (`mm`, `mtst`, `mdev`); accept and store `0x` + 30 lowercase hex chars as the lossless fallback. ## 5. Block production model

**Components and deployment mode.** The node consists of store, block-producer, network transaction builder, and RPC components; they can run as separate instances for performance or as a single process for convenience, and public testnet/devnet were documented as operating in single-process mode (<https://docs.miden.xyz/core-concepts/node/operator/architecture/>). In v0.13.4 source, `bundled start` runs store, block-producer, validator, RPC, and optionally network transaction builder in one process, binding internal component gRPC endpoints on localhost (`bin/node/src/commands/bundled.rs` at tag v0.13.4: <https://github.com/0xMiden/node/blob/v0.13.4/bin/node/src/commands/bundled.rs>).

**Public vs internal gRPC.** Inter-component gRPC is trusted and must not be public; the external RPC component is the only external-facing component (<https://docs.miden.xyz/core-concepts/node/operator/architecture/>). The public-facing proto directory explicitly separates public RPC/types from internal protocols (<https://github.com/0xMiden/node/tree/v0.13.4/proto/proto>).

**Block interval.** The block producer creates blocks periodically; v0.13.4 source defines `DEFAULT_BLOCK_INTERVAL = Duration::from_secs(3)` and `DEFAULT_BATCH_INTERVAL = Duration::from_secs(1)` (`crates/block-producer/src/lib.rs` at tag v0.13.4: <https://github.com/0xMiden/node/blob/v0.13.4/crates/block-producer/src/lib.rs>). Treat this as a node default, not a protocol finality guarantee.

**Finality semantics.** The v0.13.4 README says the node is alpha and currently developed for a centralized operator, with P2P networking and consensus to be added later (<https://raw.githubusercontent.com/0xMiden/node/v0.13.4/README.md>). The public RPC exposes `StoreStatus.chain_tip` as the latest block in the chain and `BlockProducerStatus.chain_tip` as the latest block the producer considers canonical (`proto/proto/rpc.proto`). I found no separate finalized/LIB field in the public v0.13.4 proto. For the explorer MVP, model every block returned by the canonical public RPC as **accepted/canonical** and do not expose a stronger "finalized" label until an official finality/L1-settlement API is confirmed.

## 6. Cross-references for the explorer

- `/block/:n` — powered by `miden_blocks`; show full header, roots, timestamp, validator key, tx commitment, note root, nullifier root, account root, optional MMR proof.
- `/tx/:id` — powered by `miden_transactions`; MVP may return only account-scoped transactions. Display coverage warning when the transaction was not observed through indexed accounts or decoded blocks.
- `/account/:id` — powered by `miden_accounts`; show commitment history, latest header for public accounts, storage mode, vault/storage/code roots; link to account-scoped transactions and notes where observed.
- `/note/:id` — powered by `miden_notes`; show metadata, block/index, inclusion proof, note type, details-present flag; decode public/network details when decoder exists.
- `/nullifier/:hex` — powered by `miden_nullifiers`; show consumed block and prefix coverage status; optionally verify via `CheckNullifiers` proof.
- `/search?q=` — accept block numbers, account IDs (Bech32 or 0x hex), digest-like tx/note/nullifier IDs, and root commitments.

## 7. Open questions / blockers for future agents

1. **Digest byte order for canonical hex.** Proto exposes digest lanes as `fixed64 d0..d3`, but this document's `0x` encoding convention must be verified against the official Rust SDK/CLI display format before freezing URLs and DB unique keys.
2. **Global transaction enumeration.** v0.13.4 public proto lacks a global transaction list or `GetTransactionById`; confirm whether raw `GetBlockByNumber` bytes contain decodable transaction IDs/headers and whether indexing them is stable across v0.13.x.
3. **Complete note discovery.** `SyncNotes` is tag-based and tags are best-effort filters. Define an official strategy for full-public-note coverage (all tags? raw block decode? store internals?) before claiming explorer-wide note completeness.
4. **Private-note consumption payload visibility.** Public docs/protos confirm nullifiers are public and private note details are required by the consumer, but do not clearly state which private-note data, if any, is retained in node/block storage after submitting a proven transaction. Confirm with live v0.13.4 raw block decode before documenting beyond the matrix above.
5. **Finality/L1 settlement.** No separate finalized/LIB field was found in public v0.13.4 RPC. Confirm whether Miden testnet/devnet has any finality or L1 settlement notion that should be exposed later.
6. **Account storage-mode decoding.** Docs state storage mode is encoded in the 3rd/4th most significant bits of account ID; implement and test decoding with official SDK examples before schema constraints or UI labels depend on it.
7. **Public account exhaustive indexing limits.** `GetAccount`, `SyncAccountVault`, and `SyncAccountStorageMaps` have thresholds/pagination and near-tip restrictions; future agents must test live RPC limits and decide backfill policy for large public accounts.
